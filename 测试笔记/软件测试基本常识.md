## 1. 软件测试的定义

软件测试是**为了发现程序中的错误而执行程序的过程**，也是**验证和确认软件是否满足需求、设计及预期结果的活动**。更完整的定义包括：使用人工或自动化手段运行或评估软件系统，检验其与规定需求之间的差异。

------

## 2. 软件测试的3个目的

| 目的         | 说明                                     |
| :----------- | :--------------------------------------- |
| **发现缺陷** | 找出软件中存在的错误、缺失或多余的功能   |
| **验证需求** | 确认软件是否按照需求规格说明书正确实现   |
| **建立信心** | 通过测试结果评估软件质量，为发布提供依据 |

------

## 3. 软件生命周期瀑布模型的6个阶段和主要工作

| 阶段           | 主要工作                        |
| :----------- | :-------------------------- |
| **可行性研究与计划** | 分析项目可行性，制定项目计划              |
| **需求分析**     | 收集、分析、定义用户需求，编写需求规格说明书      |
| **设计**       | 包括概要设计（架构、模块划分）和详细设计（接口、算法） |
| **编码实现**     | 编写程序代码，实现设计                 |
| **测试**       | 执行单元测试、集成测试、系统测试等           |
| **维护**       | 交付后修复缺陷、功能增强、环境适配           |

------

## 4. 黑盒测试和白盒测试的优缺点

| 测试类型     | 优点                                                         | 缺点                                     |
| :----------- | :----------------------------------------------------------- | :--------------------------------------- |
| **黑盒测试** | 不依赖代码实现，从用户角度出发；适合功能验证；测试用例与实现分离 | 无法覆盖代码内部逻辑；可能存在遗漏路径   |
| **白盒测试** | 深入代码逻辑，覆盖率高；能发现内部错误；便于优化             | 成本高，需要代码知识；无法发现缺失的功能 |

------

## 5. 单元测试、集成测试、系统测试的区别

| 维度         | 单元测试            | 集成测试       | 系统测试        |
| :--------- | :-------------- | :--------- | :---------- |
| **测试对象**   | 最小可测单元（函数、类、模块） | 模块之间的接口和交互 | 完整的软件系统     |
| **测试依据**   | 详细设计文档          | 概要设计文档     | 需求规格说明书     |
| **测试者**    | 开发人员            | 开发或测试人员    | 测试人员        |
| **发现缺陷类型** | 逻辑错误、算法错误       | 接口错误、数据流错误 | 功能缺失、性能、安全等 |
| **执行顺序**   | 最早              | 中间         | 最后          |

------

## 6. Alpha测试和Beta测试的区别

| 维度         | Alpha测试                | Beta测试             |
| :----------- | :----------------------- | :------------------- |
| **执行地点** | 开发环境（内部）         | 用户真实环境（外部） |
| **测试人员** | 内部测试人员 + 少量用户  | 最终用户（大量）     |
| **测试时间** | 系统测试之后、Beta之前   | Alpha之后、发布之前  |
| **控制程度** | 受控环境，可记录详细日志 | 非受控，用户自由使用 |
| **反馈内容** | 缺陷、易用性问题         | 缺陷、使用体验、建议 |

------

## 7. 回归测试的定义、策略

**定义**：在软件修改（修复缺陷、新增功能、重构）后，重新执行之前已通过的测试用例，以验证修改没有引入新的错误。

**常见策略**：

| 策略               | 说明                                                         |
| :----------------- | :----------------------------------------------------------- |
| **全部回归**       | 重新执行所有已有测试用例（成本高，适合小范围变更或关键系统） |
| **选择性回归**     | 只执行与被修改代码相关的测试用例（常用）                     |
| **基于风险的回归** | 根据模块风险等级、变更影响范围选择测试子集                   |
| **自动化回归**     | 使用自动化脚本快速执行大量回归测试                           |

## 8. 测试的4个活动的主要工作

通常指测试过程的4个基本活动（参照ISTQB或标准测试流程）：

| 活动         | 主要工作                                 |
| :----------- | :--------------------------------------- |
| **测试计划** | 制定测试策略、资源安排、时间表、风险评估 |
| **测试设计** | 设计测试用例、测试数据、编写测试规程     |
| **测试执行** | 运行测试用例、记录实际结果、提交缺陷     |
| **测试评估** | 分析测试结果、编写测试报告、评估质量     |

------

## 9. 质量的定义

**质量**是指**实体（产品、系统、服务）满足明确或隐含需求的能力的特性总和**。在软件工程中，常用定义是：**软件质量 = 符合需求 + 满足用户期望**。国际标准.ISO 9000定义质量为“一组固有特性满足要求的程度”。

------

## 10. ISO25010质量模型8大特性

| 序号  | 特性        | 核心关注点               |
| --- | --------- | ------------------- |
| 1   | **功能适用性** | 功能是否完备、正确、恰当        |
| 2   | **性能效率**  | 响应时间、吞吐量、资源利用率      |
| 3   | **兼容性**   | 共存性（不干扰其他系统）、互操作性   |
| 4   | **易用性**   | 可学习、可操作、界面美观、无障碍    |
| 5   | **可靠性**   | 成熟度、容错性、可恢复性        |
| 6   | **安全性**   | 保密性、完整性、不可抵赖性、可追溯   |
| 7   | **可维护性**  | 模块化、可复用、易分析、易修改、易测试 |
| 8   | **可移植性**  | 适应性、可安装、可替换         |

## 12. 常见的缺陷管理流程和缺陷报告状态

**缺陷管理流程**（以标准4状态流程为例）：

```text
发现缺陷 → 提交 → 确认 → 分配 → 修复 → 回归 → 关闭
                ↓
            （拒绝/延期）
```


**缺陷报告状态**：

| 状态         | 含义                   |
| :----------- | :--------------------- |
| **新建**     | 缺陷已提交，待处理     |
| **已确认**   | 开发或PM确认是有效缺陷 |
| **已分配**   | 指派给具体开发人员     |
| **修复中**   | 开发人员正在修复       |
| **已修复**   | 开发完成修复，待回归   |
| **回归通过** | 测试验证通过           |
| **重新打开** | 回归不通过，需重新修复 |
| **已关闭**   | 缺陷确认修复，流程结束 |
| **拒绝**     | 不是缺陷或重复缺陷     |
| **延期**     | 低优先级，后续版本处理 |

------

## 13. 缺陷报告常见的要素

| 要素            | 说明                     |
| :-------------- | :----------------------- |
| **缺陷ID**      | 唯一编号                 |
| **标题**        | 简明概括问题             |
| **严重程度**    | 致命、严重、一般、轻微   |
| **优先级**      | 立即、高、中、低         |

| **提交人/日期** | 测试人员及发现时间       |
| **指派给**      | 负责修复的开发人员       |

## 14. 软件测试的七大原则（ISTQB）

| 原则                                   | 说明                                                         |
| :------------------------------------- | :----------------------------------------------------------- |
| **测试显示缺陷存在，但不能证明无缺陷** | 测试能降低未发现缺陷的数量，但永远无法证明软件"完全正确"     |
| **穷尽测试是不可能的**                 | 在有限资源下无法覆盖所有输入/路径/场景，必须基于风险取舍     |
| **测试应尽早介入（测试左移）**         | 缺陷发现得越早，修复成本越低                                 |
| **缺陷聚集（二八定律）**               | 少数模块往往包含大部分缺陷，应把精力集中在高风险区域         |
| **杀虫剂悖论**                         | 同一用例反复执行会"免疫"——需定期评审、更新用例以发现新缺陷   |
| **测试活动依赖上下文**                 | 医疗、电商、游戏等项目的风险与策略各不相同，没有放之四海皆准的方案 |
| **无谬误谬误**                         | 没发现缺陷 ≠ 软件满足需求——需求本身可能是错的                 |

------

## 15. 验证与确认（Verification & Validation，V&V）

- **验证（Verification）**：「我们是否**正确地构建**了产品？」——检查软件是否符合规格说明（如需求/设计评审、静态测试）。
- **确认（Validation）**：「我们是否构建了**正确的**产品？」——检查软件是否满足用户真实需求（如系统测试、验收测试）。

| 维度         | 验证 Verification       | 确认 Validation             |
| :----------- | :---------------------- | :-------------------------- |
| **关注点**   | 过程与规格说明一致      | 结果与用户需求一致          |
| **典型活动** | 评审、静态分析、单元测试 | 系统测试、验收测试          |
| **回答的问题** | Are we building it right? | Are we building the right thing? |

------

## 16. 静态测试与动态测试

| 类型       | 是否运行程序 | 常用方法                       | 作用                               |
| :--------- | :----------- | :----------------------------- | :--------------------------------- |
| **静态测试** | 否           | 需求/设计/代码评审、静态分析工具 | 在编码前/早期发现缺陷，成本最低     |
| **动态测试** | 是           | 执行用例、观察实际运行行为       | 验证程序在真实运行下的结果是否正确 |

> 静态测试（如代码评审）往往能以十分之一的成本发现动态测试后期才能暴露的问题。

## 17. 软件测试分类总览

从不同维度对测试进行划分，便于在设计测试策略时"对号入座"：

| 分类维度         | 主要类别                                                     |
| :--------------- | :----------------------------------------------------------- |
| **是否执行代码** | 静态测试 / 动态测试                                          |
| **是否关注内部** | 黑盒 / 白盒 / 灰盒（关注内部结构与外部表现的交集，如接口测试） |
| **执行方式**     | 手工测试 / 自动化测试                                        |
| **测试阶段**     | 单元测试 / 集成测试 / 系统测试 / 验收测试（见第 5 节）        |
| **测试目标**     | 功能测试 / 非功能测试（性能、安全、兼容、易用…）              |

## 18. 测试用例设计方法

写好用例的核心是**用最少用例覆盖最多场景**。常用黑盒设计方法：

| 方法             | 思路                                                         | 适用场景                                   |
| :--------------- | :----------------------------------------------------------- | :----------------------------------------- |
| **等价类划分**   | 把输入域划分为有效/无效等价类，每类取一个代表值              | 输入取值范围大、组合多的字段               |
| **边界值分析**   | 针对等价类的边界（上点、离点、内点）设计用例——最易出错处     | 与等价类配合，数值/长度型输入              |
| **判定表/因果图** | 梳理多条件组合逻辑，列出条件桩与动作桩                       | 输入条件相互制约、规则复杂的业务           |
| **场景法**       | 按业务流程拆成基本流与备选流，沿路径设计用例               | 有明确业务流的模块（如登录、下单）         |
| **正交试验法**   | 用正交表在"多因素多水平"下用最少组合覆盖两两交互             | 配置项、参数组合极多的测试                 |
| **状态迁移法**   | 梳理对象状态及迁移条件，覆盖所有状态与合法/非法跳转          | 有状态机特征的模块（如订单、审批）         |
| **错误推测法**   | 基于经验/历史缺陷，推测易错点重点验证                        | 补充设计、回归、探索性测试                 |

**小例子（等价类 + 边界值）**：某年龄输入框限定 `18 ≤ 年龄 ≤ 60`。

- 有效等价类：`[18, 60]` → 取 30
- 无效等价类：`<18`、`>60` → 取 10、70
- 边界值：17、18、19、59、60、61（边界及相邻值最易出错）

## 19. 软件测试模型

| 模型   | 核心思想                                                     | 特点                                   |
| :----- | :----------------------------------------------------------- | :------------------------------------- |
| **V 模型** | 开发阶段（需求→设计→编码）与测试阶段（验收←系统←集成←单元）一一对应 | 强调测试与开发阶段的对应，但测试介入偏晚 |
| **W 模型** | 在 V 基础上，测试与开发**并行**，文档/需求阶段即开始评审     | 测试伴随整个生命周期，左移更彻底         |
| **H 模型** | 测试活动独立成"流"，只要就绪即可尽早、迭代执行               | 灵活，强调测试准备与执行分离             |
| **X 模型** | 强调探索性测试、交叉测试，更贴近敏捷实践                     | 注重非预定义的、经验驱动的发现           |
| **敏捷测试** | 迭代内完成测试，持续集成 + TDD/BDD，测试是全员责任           | 快速反馈，用例轻量、可自动化             |

## 20. 测试左移与测试金字塔

- **测试左移（Shift Left）**：把测试活动尽量前移到需求、设计阶段，在缺陷最便宜时被消灭。
- **测试金字塔（Test Pyramid）**：合理的投入比例是 **单元测试（大量）＞ 集成/接口测试（中等）＞ UI/E2E 测试（少量）**。应避免"倒金字塔"——过多脆弱、昂贵、易失败的 UI 自动化。

| 层级           | 比例 | 代表工具                                  |
| :------------- | :--- | :---------------------------------------- |
| 单元测试       | 多   | JUnit、pytest                             |
| 集成/接口测试  | 中   | Postman、pytest + requests                |
| UI / E2E 测试  | 少   | Selenium、Playwright（见 [[01-环境搭建\|Selenium 自动化]]） |

## 21. 缺陷严重程度与优先级（细化第 13 节）

第 13 节已列出缺陷要素，这里明确**严重程度**与**优先级**的区别——两者常被混淆，但并不相等。

| 概念       | 含义                                   | 判定视角     | 常见分级                         |
| :--------- | :------------------------------------- | :----------- | :------------------------------- |
| **严重程度** Severity | 缺陷对系统的**技术影响**有多大         | 技术/质量    | 致命 / 严重 / 一般 / 轻微 / 建议 |
| **优先级** Priority   | 缺陷应**多快被修复**（业务先后次序）   | 业务/排期    | 紧急 / 高 / 中 / 低               |

**二者关系**：严重程度高 **通常** 对应优先级高，但**不绝对**：

- 严重但不常触发的路径（如小众浏览器的边缘崩溃）→ 严重程度高、优先级中低；
- 轻微但高曝光的问题（如首页错别字、按钮错位）→ 严重程度低、优先级高（公关/体验风险）。

> 定级建议：先判严重程度（技术事实），再结合出现频率、影响范围、上线节点定优先级（业务决策）。

## 22. 非功能测试简介

除功能测试外，"质量"还来自非功能维度（对应第 10 节 ISO25010）：

| 类型         | 关注点                                       | 常用工具/方法                                |
| :----------- | :------------------------------------------- | :------------------------------------------- |
| **性能测试** | 负载、压力、并发、稳定性、响应时间           | JMeter（见 [[jmeter性能测试\|JMeter 性能测试]]）、LoadRunner、k6 |
| **安全测试** | SQL 注入、XSS、越权、敏感信息泄露            | ZAP、Burp Suite（建议专业工具/团队）         |
| **兼容性测试** | 不同 OS / 浏览器 / 分辨率 / 设备适配        | 多浏览器矩阵、云真机平台                     |
| **易用性测试** | 用户体验、可访问性（a11y，WCAG 合规）       | 用户走查、axe-core、屏幕阅读器验证           |
| **可靠性测试** | 长时间运行、故障恢复、数据一致性             | 长时间压测、混沌工程、故障注入               |

## 23. 手工测试与自动化测试

两者互补，不是替代关系——**该用手工的地方别硬上自动化，该自动化的地方别死扛手工**。

| 维度     | 手工测试                                   | 自动化测试                                         |
| :------- | :----------------------------------------- | :------------------------------------------------- |
| **适用** | 探索性、一次性、UI 频繁变动、用户体验评估  | 回归、数据驱动、重复执行、性能/压力、夜间批量       |
| **优点** | 灵活、起步成本低、能发现主观体验问题       | 执行快、可重复、覆盖广、可无人值守（夜间/CI）       |
| **缺点** | 慢、易疲劳出错、难以大规模重复             | 前期投入大、脚本需维护、难以评估主观体验           |
| **工具** | —                                          | Selenium/Playwright（UI）、JMeter（性能）、Postman（API） |

> 自动化性价比公式：**收益 = 执行次数 × 单次节省时间 − 脚本开发维护成本**。低频、易变、一次性的用例，手工更划算。
