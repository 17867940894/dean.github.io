## 二、从测试工程师视角的拆解

"用 AI 重构老项目接入 AI 工作流"——这件事对测试工程师不是旁观者，而是**成败的关键护栏**。结合端测测的职责（回归测试、测试策略、关键路径、验收 harness），拆解如下：

### 1. 重构老项目的第一要务：先有「回归测试基线」
AI 重构最怕的不是改不动，而是**改坏旧功能还不知道**。
- 动手前必须存在可执行的自动化回归基线（单元 + 集成优先，E2E 保关键路径）。
- 遵循**测试金字塔**：70% 单元 + 20% 集成 + 10% E2E，不倒金字塔。
- **关键用户旅程 100% 覆盖**（登录/核心业务流/支付等），边角按优先级。
- 没有基线就上 AI = 给技术债加杠杆，风险指数级放大。

### 2. 验收机制（Harness）= 测试左移的 CI 门禁
UP 主合集里"Harness 如何长出来""验收结果"正是端测测眼中的**测试收口**：
- 重构每一步都要有可跑的校验（对应 CI 里的测试门禁 / 质量闸门）。
- "没有 harness 的 AI 重构 = 裸奔"——每次 AI 改动后必须自动跑基线，红就停。
- 验收标准要**可读、可执行**：用 `should_...when_...` 命名，AAA 结构（Arrange/Act/Assert）。

### 3. 分模块多 Agent 拆解 → 必须有「接口契约测试」
视频提示可按多模块多 Agent 并行加速，这带来新的测试命题：
- 模块边界先定**契约测试（Contract Testing）**，防止各 Agent 各改各的、接口对不上。
- 重构改动 DOM/结构时，**不依赖脆弱选择器**：优先级 `data-testid` > 语义角色 > 文本 > CSS class。
- 并行重构后要补一次**跨模块集成回归**，验证拼接处无回归。

### 4. 风险与稳定性纪律
- AI 产出有 flaky 倾向，**稳定胜过速度**：宁可慢一点，也不能要一条不稳定的"假绿"测试。
- 测试数据要**自动清理**，不污染测试/生产环境。
- 紧急热修时不一刀切拦截：给"最小必要测试 + 灰度 + 事后补齐"的分阶段建议。

## 三、可落地的测试行动清单（重构老项目接入 AI 工作流）

| 阶段 | 测试动作 | 产出 |
|------|----------|------|
| **立项前** | 梳理核心用户旅程，补齐自动化回归基线 | 可跑的测试套件（单测/集成/E2E） |
| **拆解阶段** | 为每个模块定义接口契约 + 验收 spec | 契约测试 + 验收标准文档 |
| **重构中** | 小步提交，每步跑 harness（CI 门禁） | 每次提交红/绿可见，旧功能零回归 |
| **验收** | 关键路径 E2E 全绿 + 性能对照（不退化） | 验收报告 + 性能基线对比 |
| **上线** | 最小必要测试 + 灰度发布 + 事后补齐 | 灰度方案 + 补测计划 |

## 四、一句话总结

> **"用 AI 重构老项目"本质是给老项目装上「测试安全带」再松手——没有回归基线和验收 Harness，AI 提效只是给技术债加杠杆。**

这正好印证端测测的信条：**好的测试不是抓 bug，是让团队敢发布。**
