# Claude Code 删掉 80% 系统提示词：新一代模型的上下文工程实践

> 来源：Anthropic 技术成员 Thariq Shihipar 公开分享，经「Python 见习室」整理编译。

## 核心发现

- 在 Claude Opus 5 / Fable 5 等新一代强推理模型上，Anthropic 删除了 Claude Code 系统提示词中 **80% 以上** 的内容，编码评估未观察到可测量的性能损失。

- 模型越强，越不需要「保姆式」指导。冗长的手写规则除了浪费 token，还可能让效果变差。

- 新范式：**CLAUDE.md 保持绝对精简**——高绩效团队控制在 60 行以内，通常绝不超过 300 行；特定任务的上下文交给 Skill（技能）承载。

- 趋势：提示词工程正在向「上下文工程（context engineering）」的整体架构高度转变。

## 从提示词工程到上下文工程

- 上下文 = 系统提示词 + Skills + CLAUDE.md + 记忆 + 其他来源，跨多个请求复用，因此无法写得过于具体。

- 当用户发一条消息时，提示词只是模型所获上下文的一小部分，其余来自上述长期来源。

- 内置工具 `claude doctor`（Claude Code 中执行 `/doctor`）可自动把 Skills 和 CLAUDE.md 调整到合适规模。

## 昔 → 今：六组范式转变

| 旧做法             | 新做法           | 说明                                                                                                                            |
| --------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 给 Claude 定规则    | 让 Claude 自行判断 | 旧模型靠强约束规避最坏情况（如禁止写注释）；新模型判断力足够，无需显式规则。例：旧规则「默认不写注释、绝不多行 docstring」→ 新规则「代码读起来要像周围代码：匹配注释密度、命名与惯用法」。                           |
| 给 Claude 举例子    | 设计好接口         | 示例会把模型约束在特定探索空间；应把精力放在工具/脚本/文件设计上（参数如何更具表达力）。例：Todo 工具把状态列为「待处理/进行中/已完成」枚举值，即可提示用法；「始终只保留一项进行中」清晰界定期望行为。                      |
| 一股脑全写在前面        | 渐进式披露         | 非总用得上但关键的内容（如代码评审、验证）拆成独立 Skill，按需调用；部分工具「延迟加载」（先 ToolSearch 检索定义再调用）；CLAUDE.md/SKILL.md 也应构建文件树，按时机加载。                       |
| 反复强调            | 简洁的工具描述       | 早期模型需重复指令、更听信窗口末尾内容；现可删掉重复：把使用说明放进工具描述，而非系统提示词。                                                                               |
| 把记忆写进 CLAUDE.md | 自动记忆          | 旧流程用 `#` 快捷键写入 CLAUDE.md 持久化记忆；现 Claude 会自动保存与当前工作及用户相关的记忆。                                                                   |
| 简单的规格文档         | 丰富的参考材料       | Claude 已能驾驭更复杂参考材料：除 markdown 计划文件外，可引用 artifacts 生成的 HTML；也可用代码本身作参考（如详尽测试用例、待移植函数）；评分标准（rubric）可派生 verifier agents 还原开发者品味。 |

## 落地到自己的上下文

### 系统提示词

与产品语境高度绑定，告诉 Claude 身处什么产品、在做什么。对 Claude Code 基本不改；若自建 agent harness，此处值得重点投入。

### CLAUDE.md

- 保持轻量：简要说明仓库用途，把大部分 token 花在代码库的「坑」上（如「所有类型定义集中在一个大文件、别处没有」这类信息）。

- 避免写 Claude 看一眼文件结构/仓库就能知道的「显而易见」之事。

- 更细内容用渐进式披露：如多套独特验证流程，做成验证 Skill 后在 CLAUDE.md 中引用。

### Skills

- 视为轻量指南，让 Claude 按需找到信息；除非极关键领域，不过度约束。

- 篇幅较长的 Skill 尽量渐进式披露，拆成多文件分而治之。

- 最有价值之处：承载开发者本人/团队/产品特有的观点、知识与最佳实践。

### 参考材料

- 用 `@` 提及文件引入，供 Claude 查阅计划深层细节。

- 优先选择代码形式的文件（高保真、Claude 熟悉的语言）；一份 HTML 设计稿通常优于文字描述或截图。

- 规格说明可是一套测试用例，或另一个代码库中待移植的函数。

## 行动建议

- 在系统提示词、Skills、CLAUDE.md 三者之间做一轮简化（Anthropic 自身也这么做）。

- 直接用 `claude doctor` 命令自动完成规模调整。

## 关键提醒

- 约束的必要性随模型能力递减：旧规则大多用于规避最坏情况，新模型可依据上下文与自身判断行事。

- 避免指令冲突：系统提示词、Skills、用户请求互相矛盾（如一边「酌情保留文档」、一边「禁止添加注释」）会迫使模型在冲突间反复权衡，徒耗算力。
