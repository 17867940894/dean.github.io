## 一、认知重构——从“人写”到“AI 协作”的测试架构

### 1.1 传统测试工程 vs AIGC-TCE 对比

| 维度           | 传统测试工程（Traditional）              | AIGC-TCE（AI 驱动）                              |
| -------------- | ---------------------------------------- | ------------------------------------------------ |
| **需求理解**   | 人工阅读 PRD，依赖经验脑补隐性需求边界   | LLM 语义解析，自动提取语义特征                   |
| **设计逻辑**   | 手写用例，依赖常用模板（等价类、边界值） | 基于模型推演，自动生成覆盖路径                   |
| **覆盖深度**   | 受限于交付时间，通常只覆盖正向和显性路径 | AI 自动探索异常流、并发冲突等隐性场景            |
| **颗粒度控制** | 颗粒度不一，因人而异，难以标准化         | 通过 Prompt 约束，实现颗粒度高度一致             |
| **维护成本**   | 需求一变，全量人工更新，极易滞后         | 需求变更输入，AI 自动进行 Diff（差异）分析并同步 |

### 1.2 AIGC-TCE 的三大优势

#### 1.2.1 消除“冷启动”焦虑

| 方式          | 说明                                                         |
| ------------- | ------------------------------------------------------------ |
| **传统方式**  | 面对新复杂模块，测试负责人需花 1-2 天熟悉文档                |
| **AIGC 优势** | 秒级解析。AI 能在几秒内给出 60%-70% 完整度的初稿，将测试人员的工作重心从“从 0 到 1 的编写”转移到“从 1 到 100 的评审与微调” |

#### 1.2.2 隐含逻辑的“显性化”

| 方式          | 说明                                                         |
| ------------- | ------------------------------------------------------------ |
| **传统方式**  | 资深测试能测出 Bug 是因为“直觉”，很难传承                    |
| **AIGC 优势** | LLM 训练语料中包含海量故障模式。能基于 PRD 自动提示：“如果用户在支付瞬间切换网络会怎样？”这种**启发式测试（Heuristic Testing）** 的能力被 AI 平民化 |

#### 1.2.3 测试资产的“原子化”与“组装化”

| 方式          | 说明                                                         |
| ------------- | ------------------------------------------------------------ |
| **传统方式**  | 用例是一整段文字，复用性差                                   |
| **AIGC 优势** | 将测试逻辑解耦。需求变成 Prompt 的一部分，步骤变成组件，AI 根据不同的测试目标（冒烟、全量、回归）自动组装不同的测试路径。**核心优势**：测试资产的复用性强，可维护性强。例如登录从“账号密码”变为“扫码登录”，传统需手动修改几百个用例，AI 只需调整原子动作库 |

### 1.3 AI 与传统测试人员的优势实战对比

**案例场景**：电商平台“0元秒杀”高并发抢购场景

#### PRD 需求说明书

```text
1. 核心业务规则 (Business Rules)
   库存控制：全局库存仅 100 件。必须严格保证不超卖（卖出 > 100）且不破损（因系统
   异常导致实际订单数 < 100）。
   限购策略：同一用户 ID、同一收货手机号、同一设备 ID，在整个活动期间仅限抢购 1 件。
   订单时效：秒杀成功后，订单进入“待发货”状态（0元订单无需支付，但需在 5 分钟内
   完善收货地址，否则自动释放库存）。
   前置准入：用户必须完成实名认证，且账号等级需达到 V2 以上。

2. 交互逻辑需求 (UX & Flow)
   倒计时预热：活动开始前 1 小时进入预热态，下单按钮置灰。
   动态抢购：活动开始瞬间，按钮变为高亮可点击。
   排队等待：点击后不直接返回结果，而是进入“排队中”状态，前端轮询后端结果（缓解
   数据库瞬时压力）。
   售罄反馈：库存清零后，后端需在 100ms 内同步状态给前端，按钮变更为“已抢光”。

3. 系统架构约束 (Architecture)
   流量削峰：系统需接入 CDN 静态资源加速，防止抢购时的静态请求压垮服务器。
   Redis 预减库存：为了性能，库存必须在 Redis 中进行预减，而不是直接操作 MySQL。
   消息队列（MQ）：抢购成功后，通过 MQ 异步生成订单，实现应用解耦。

4. 风控与安全需求 (Security & Anti-Fraud)
   黑名单拦截：命中黑名单库的用户直接返回“活动火爆”。
   接口隐藏：秒杀接口 URL 必须是动态生成的，防止自动化脚本提前扫描。
   验证码挑战：针对同一 IP 的高频请求，强制弹出图形验证码或滑动滑块。
   限流降级：当并发量超过系统承载能力（如 10w QPS）时，系统自动触发熔断，返回友
   好提示页。
```

### 1.4 AIGC-TCE 实践的四个核心支柱

#### 1.4.1 从“单点生成”转向“全链路工程化”（From Point to Pipeline）

| 方式              | 说明                                                         |
| ----------------- | ------------------------------------------------------------ |
| **传统做法**      | 给 AI 一段话，它写几个用例，叫“点对点辅助”                   |
| **AIGC-TCE 理念** | AI 参与需求的审计、用例的设计、脚本的生成、执行结果的分析以及脚本的维护 |

#### 1.4.2 需求数字化：建立项目的“数字孪生大脑”（Requirement as Data）

| 方式         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **核心理念** | 需求文档（PRD）不应只是 Word 文档，而应是 AI 可理解的结构化知识库 |
| **落地做法** | 利用 RAG（检索增强生成）技术，把 PRD 变成向量数据            |

#### 1.4.3 测试思维的“逻辑拓扑”化（Logical Topology）

| 方式         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **核心理念** | 用例不是凭空生成的，是基于业务逻辑图（Topology）生成的       |
| **落地做法** | 让 AI 先根据 PRD 画出逻辑流图（如 Mermaid 流程图），再基于流程图的路径（全路径覆盖、边界值、判定表）拆解用例 |

#### 1.4.4 闭环自愈与进化（Self-Healing & Evolution）

| 场景                            | 说明                                                         |
| ------------------------------- | ------------------------------------------------------------ |
| **需求变更自动同步**            | 需求文档（PRD）更新后，AI 对比新旧需求，识别变更（如“登录流程增加了图形验证码”），自动在原子动作库中插入验证码处理步骤，重新生成受影响用例。实现“需求变，用例即变” |
| **线上 Bug 自动转化为测试用例** | 将生产环境错误日志和用户行为轨迹输入 LLM，AI 分析根因，自动生成针对该漏洞的“特征测试用例”，永久加入回归测试库。整个测试体系通过吸取“失败经验”自动生长，越测越聪明 |

### 1.5 小总结

**AIGC-TCE** 是生成式 AI 驱动的测试用例全生命周期工程方法论，核心是将 AIGC 技术深度融入测试用例的“需求分析→设计生成→执行验证→评估优化→维护退役”完整闭环（含需求审计、测试用例审计、执行审计等），通过**“智能生成 + 人机协同 + 数据驱动 + 持续进化”** 四大支柱，解决传统测试用例管理中“效率低、覆盖难、维护贵、质量不稳定”的核心痛点，实现测试质量与效率的双重飞跃。

> 在传统工程中，测试用例是**“写”**出来的，受限于你的体力；在 AIGC 时代，测试用例是**“生”**出来的，只受限于你的想象力（Prompt 的深度）。

### 1.6 测试专用的提示词工程（Prompt Engineering for Testers）

三大核心能力：

- **角色设定（Role-Play）** ：如何让 AI 扮演资深测试架构师
- **上下文注入（Context Injection）** ：如何喂给 AI 业务背景数据
- **输出约束（Chain of Thought）** ：如何引导 AI 遵循等价类、边界值等逻辑

#### 通用核心结构（5 个核心模块）

| 模块            | 说明                                       | 示例                                                         |
| --------------- | ------------------------------------------ | ------------------------------------------------------------ |
| **1. 角色设定** | 给 AI 分配具体角色，使输出更贴合场景专业度 | “你是一名资深 Python 开发工程师”                             |
| **2. 任务目标** | 用简洁直白的语言描述 AI 需要完成的具体任务 | “写一篇面向青少年的环保主题短文，重点讲塑料污染的危害，字数 500 字左右” |
| **3. 约束条件** | 明确输出的格式、风格、禁忌等               | “输出格式为 Markdown 表格，语言简洁正式”                     |
| **4. 输出格式** | 指定输出的结构或格式                       | “以‘问题-原因-解决方案’的结构输出”                           |
| **5. 示例参考** | 提供示例，帮助 AI 精准对齐预期             | 参考格式：“【产品名称】-【核心功能】-【适用人群】”           |

#### 场景化提示词模板

**模板 1：功能测试用例设计**

```text
角色：[具体角色，如“资深功能测试工程师”]
任务：[具体需求，如“为用户登录模块设计功能测试用例，被测系统为 Web 版电商平台”]
需求背景：
1. 登录方式：支持手机号+验证码、账号密码两种登录方式；
2. 核心规则：密码错误 3 次锁定账号 1 小时，验证码有效期 5 分钟；
3. 兼容要求：适配 Chrome、Edge、Firefox 最新版浏览器。
约束：
1. 用例需覆盖正向测试、反向测试、边界值测试、兼容性测试；
2. 每个用例包含“用例 ID、模块、标题、前置条件、操作步骤、预期结果、优先级”7 个要素；
3. 优先级分为 P0（核心）、P1（重要）、P2（一般）。
输出格式：Markdown 表格，按优先级降序排列。
```

**模板 2：Bug 报告撰写**

```text
角色：[具体角色，如“软件测试工程师”]
任务：[具体需求，如“针对电商平台商品结算页的‘优惠券无法使用’问题撰写 Bug 报告”]
Bug 实际情况：
1. 触发场景：选择满 200 减 30 优惠券，结算金额 250 元时，点击“使用优惠券”无响应；
2. 复现步骤：①登录账号→②加入 250 元商品到购物车→③进入结算页→④选择满 200 减 30 优惠券→⑤点击“使用优惠券”按钮；
3. 环境信息：Chrome 120.0 版本、Windows 11 系统、账号：test123；
4. 预期结果：优惠券正常生效，结算金额扣除 30 元；
5. 实际结果：按钮点击无响应，优惠券未生效，控制台无报错。
约束：
1. 包含 Bug 等级（严重/高/中/低）、模块、环境、复现步骤、预期结果、实际结果、附件说明；
2. Bug 等级判定：影响核心交易流程，标记为“高”等级。
输出格式：按“基本信息-复现步骤-预期 vs 实际结果-补充说明”结构呈现。
```

#### 常见误区

| 误区         | 说明                                         |
| ------------ | -------------------------------------------- |
| **过度简洁** | 仅写“写代码”“做分析”，AI 无法判断具体需求    |
| **信息冗余** | 堆砌无关内容，干扰 AI 抓取核心需求           |
| **格式混乱** | 多任务混写且无结构划分，导致 AI 遗漏部分需求 |

#### 小总结

虽然 AI 提示词没有强制标准，但遵循 **“角色（背景）- 任务（目标）- 约束 - 格式 - 示例”** 的通用结构，结合场景化模板优化，能显著提升 AI 输出的精准度。

## 二、需求解析——基于 RAG 的需求知识内化与转化

### 2.1 什么是 RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 在深度融合 AI 的工作中，是解决“AI 瞎编（幻觉）”和“AI 不懂内部业务”的核心技术。

简单来说，RAG 就是给 LLM（大模型）配了一个“随时可查阅的图书馆”。

#### 直观类比

| 方式                   | 类比               | 说明                                                         |
| ---------------------- | ------------------ | ------------------------------------------------------------ |
| **纯 LLM（如 GPT-4）** | 参加闭卷考试的学生 | 记忆力惊人，但若考题涉及公司私有 API 文档或刚写的 PRD，没背过就只能凭感觉“瞎编” |
| **RAG 模式**           | 参加开卷考试的学生 | 手边有精准的《业务操作手册》，遇到问题先翻书（检索），找到相关段落（上下文），再结合语言能力总结答案 |

![第13页图片](./assets/p0001_03.png)

#### RAG 的核心工作流程

| 阶段                        | 说明                                                         |
| --------------------------- | ------------------------------------------------------------ |
| **1. 数据索引（Indexing）** | 将测试资产（PRD、历史 Bug 库、API 定义、测试规范）拆成小块（Chunks），利用 Embedding 模型把文字转为向量（数学坐标），存入向量数据库（如 Milvus、Pinecone） |
| **2. 检索（Retrieval）**    | 当用户问“请针对‘下单’模块生成测试用例”时，系统先去向量数据库搜索最接近“下单”业务逻辑的文档 |
| **3. 增强（Augmentation）** | 将检索到的“干货”拼接在 Prompt 里：“已知以下业务规则：[检索到的文档片段]。请根据这些规则生成用例。” |
| **4. 生成（Generation）**   | LLM 阅读具体“参考资料”后，生成精准的用例，不再有“幻觉”       |

#### RAG 在 AIGC-TCE 工程中的实战价值

| 痛点                  | RAG 的解决方案                      | 效果                               |
| --------------------- | ----------------------------------- | ---------------------------------- |
| 通用模型不懂私有业务  | 将公司的 Swagger/Wiki/Jira 喂给 RAG | AI 对准业务逻辑，对准字段          |
| 模型 Context 长度有限 | RAG 只挑出最相关的部分取用          | 解决几万字文档放不进 Prompt 的问题 |
| 测试标准不统一        | 将公司《测试用例编写规范》放入 RAG  | AI 生成的格式永远符合公司标准      |

### 2.2 什么是 Agent

在 AIGC-TCE 中，如果说 RAG 是给 AI 装备了一个“高性能图书馆”，那么 **Agent（智能体）** 就是给 AI 装上了“四肢和工具箱”。

在测试领域，Agent 是从“对话框生成”走向“自主任务执行”的质变。

#### Agent 的核心定义

**Agent = LLM（大脑） + 规划（Planning） + 记忆（Memory） + 工具使用（Tool Use）**

| 类型                | 定位               | 特点                                                         |
| ------------------- | ------------------ | ------------------------------------------------------------ |
| **传统 AI（LLM）**  | “博学但瘫痪”的学者 | 能写出测试方案，但无法打开浏览器或改代码                     |
| **智能体（Agent）** | “实习测试工程师”   | 懂理论，能根据目标自主拆解步骤，调用测试工具（Playwright、Postman、SQL 客户端）完成任务 |

#### RAG 与 Agent 的协作关系

| 技术      | 角色   | 解决的问题                           | 类比                             |
| --------- | ------ | ------------------------------------ | -------------------------------- |
| **RAG**   | 知识库 | 解决 AI “不知道”或“乱说”的问题       | 查阅《测试规范》和《需求文档》   |
| **Agent** | 执行者 | 解决 AI 只有“脑子”，“没法干活”的问题 | 登录系统、点点看、提 Bug、改脚本 |

**协作示例**：当指令为“分析昨晚失败的自动化脚本并修复”时：

1. Agent 启动任务，先通过 RAG 查阅最新的需求变更记录
2. Agent 调用工具（浏览器）观察页面报错
3. Agent 自主决定结合 RAG 的知识和报错信息，修改哪个定位符
4. Agent 修改代码并重新运行校验

#### Agent 的四大核心能力

| 能力                                    | 说明                                                         |
| --------------------------------------- | ------------------------------------------------------------ |
| **① 规划（Planning）**                  | 把复杂测试目标拆解成子任务。如：A. 初始化测试数据 → B. 登录并搜索商品 → C. 如果遇到弹窗，先关闭弹窗（自主决策） |
| **② 记忆（Memory）**                    | 短期记忆：记录本次测试已点击的按钮，避免死循环；长期记忆：记住项目常出 Bug 类型，测试时重点关注 |
| **③ 工具使用（Tool Use）**              | 调用 API 接口构造数据、UI 自动化框架操控浏览器、数据库校验落库结果 |
| **④ 反思与自我修正（Self-Reflection）** | 执行失败时不会直接报错，而是反思（“是不是我点击得太快了？元素被遮挡了？”）并切换策略重新执行 |

### 2.3 RAG 技术选型对比

| 选型路径         | 代表工具                               | 入门难度 | 入门难度说明                                                 | 核心优势                                                     |
| ---------------- | -------------------------------------- | -------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **SaaS 应用类**  | Coze（扣子）、豆包企业版、ChatGPT 插件 | ★☆☆☆☆    | 零代码，无需编程和部署，1 小时内可完成基础 RAG 知识库搭建    | 上手即用，插件生态丰富，核心功能免费，支持快速部署至多渠道   |
| **低代码平台类** | Dify、MaxKB、BetterYeah AI             | ★★☆☆☆    | 少量运维知识即可上手，1-3 天可完成搭建，支持本地/私有化部署  | 可视化拖拽编排，支持多种大模型切换，支持私有化部署，内置核心功能 |
| **集成框架类**   | LangChain、LlamaIndex、RAGFlow         | ★★★★☆    | 需扎实 Python 编程能力，掌握向量数据库、大模型 API 调用，1-2 周跑通 Demo | 灵活性最高，可按需定制全环节；行业标准框架，社区资源丰富；无厂商绑定 |
| **云服务原生类** | AWS Bedrock、百度千帆、阿里云灵积      | ★★★☆☆    | 需了解云服务基础操作，掌握 API 调用，3-7 天完成集成          | 企业级稳定性，按量计费成本可控，内置安全合规机制，支持多种大模型切换 |

**补充选型建议**：

- 非技术人员/快速验证场景 → **SaaS 应用类（Coze）**
- 企业级需求、需保障数据安全 → **低代码平台类（Dify）**
- 有定制化需求、具备技术团队 → **集成框架类（LangChain）**
- 企业级高并发、免运维需求 → **云服务原生类（百度千帆等）**

### 2.4 基于 Dify 在本地环境构建 RAG

#### 一、提前准备工作

1. 安装 Git
2. 安装 Ollama
3. 安装 Docker
4. 配置 Docker 国内镜像源（拉镜像速度提升 10 倍+）

**配置 Docker 国内镜像源**：

打开 Docker Desktop → 点击右上角「设置」（齿轮图标）→ 选择左侧「Docker Engine」→ 在 JSON 配置框中添加镜像源：

```json
{
  "registry-mirrors": [
    "https://mirror.aliyuncs.com",        // 阿里云通用镜像源（推荐）
    "https://docker.mirrors.ustc.edu.cn", // 中科大镜像源（备用）
    "https://hub-mirror.c.163.com"        // 网易镜像源（备用）
  ],
  "builder": {
    "gc": {
      "defaultKeepStorage": "20GB",
      "enabled": true
    }
  },
  "experimental": false,
  "features": {
    "buildkit": true
  }
}
```

点击「Apply & restart」，Docker 自动重启并应用配置。

#### 二、安装 Dify

```bash
# 1. 克隆代码库（找一个有足够磁盘空间的目录）

# 2. 进入 docker 目录
cd dify/docker

# 3. 复制环境变量配置文件
cp .env.example .env

# 4. 拉取镜像并启动 Dify 服务
docker-compose up -d

# 5. 验证启动状态（所有服务状态应为 Up，绿色）
docker-compose ps
```
